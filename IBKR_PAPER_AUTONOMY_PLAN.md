# IBKR Paper Autonomy Plan

## Purpose

Define and implement a self-sustaining algorithmic paper trading system on a single IBKR paper account that:

- runs daily with minimal manual intervention
- selects and rotates strategies based on measured performance
- tracks performance and risk at both portfolio and strategy levels
- learns from local paper environments and improves over time
- optionally uses market or stock sentiment as a regime signal when it proves useful

## Primary Goals

1. Operate one IBKR paper account as the real execution venue.
2. Simulate multiple internal "mock accounts" (virtual sleeves) inside that one IBKR account.
3. Keep each sleeve's equity, cash, positions, and PnL independent and continuously updated.
4. Select strategies and rotate them using configurable, evidence-based rules.
5. Maintain strict risk controls at both sleeve and whole-account levels.
6. Support continuous evaluation and improvement from local paper strategy outputs.
7. Produce reliable daily, weekly, and monthly performance diagnostics.

## Scope

In scope:

- IBKR paper account execution flow
- internal sleeve accounting model
- strategy selection and rotation framework
- parameterized configuration for windows, thresholds, risk, and cadence
- daily scheduler and reporting jobs
- integration of local paper test environments as challenger signal sources
- sentiment/regime feature testing and controlled adoption

Out of scope for initial version:

- live broker deployment
- auto-generated strategy code
- fully automated parameter search with no governance controls

## Key Architectural Decision

Decision: keep existing `accounts` semantics for external broker accounts and add new sleeve-specific tables.

Rationale:

- `accounts` typically models custody/broker entities (IBKR paper/live).
- Sleeves are internal books/allocations with independent NAV and ledgers.
- Mixing these concerns increases risk of logic and reconciliation regressions.

Conclusion:

- Do not overload `accounts` with virtual-sleeve behavior.
- Add explicit sleeve domain entities linked to one broker `account_id`.

## Operating Model

### Account Model

- One IBKR paper account (example: total equity `$100,000`).
- Split into internal sleeves (example: five sleeves with initial `$20,000` each).
- Each sleeve maps to one strategy or one strategy+parameter variant.

### Sleeve Lifecycle

- Sleeve starts with initial cash/equity allocation.
- Orders are generated by sleeve ownership.
- Fills update only the originating sleeve ledger and positions.
- Sleeve buying power adapts as equity changes from gains/losses.

### Portfolio-Level Reality

- IBKR margin/cash/netting remains account-level.
- Internal sleeve accounting must be reconciled against broker-level constraints.
- A global risk gate may rescale or block sleeve orders when account-level limits are hit.

## Strategy Selection and Rotation Policy

### Baseline Selection Score

Start with weighted scoring:

`score = w1 * risk_adjusted_return + w2 * stability - w3 * drawdown - w4 * cost_drag + w5 * regime_fit`

### Rotation Gates

Rotate incumbent only when challenger:

1. has minimum sample size in the configured rolling window
2. outperforms by configured threshold
3. passes risk limits (drawdown/turnover/concentration)
4. is outside rotation cooldown lock

### Rotation Mode

- Champion/challenger model:
  - incumbent trades live in sleeve
  - challengers run in shadow evaluation
- Rotate only on threshold evidence, not noise

## Virtual Sleeve Accounting Rules

1. Sleeve NAV updates continuously:
`sleeve_equity = sleeve_cash + market_value(open_positions)`

2. Trade attribution:
- realized PnL, fees, and slippage are sleeve-local
- no cross-sleeve contamination of performance

3. Capital drift:
- sleeve capital is not fixed at initial allocation
- each sleeve size capacity follows current sleeve equity

4. Shared-account constraints:
- if account-level constraints bind, apply deterministic rescaling policy:
  - priority-based, proportional, or risk-budget-based

5. Symbol conflicts:
- define and enforce one policy:
  - allow overlap
  - cap overlap
  - net conflicts at portfolio layer

## Sentiment and Regime Integration

Phase approach:

1. Phase A:
- use sentiment only as regime classifier input (risk-on/risk-off, trend/chop)

2. Phase B:
- include regime fit in score with low initial weight

3. Phase C:
- retain only if out-of-sample lift is persistent after costs

Rule:

- sentiment should not be a direct trade trigger in initial rollout

## Job Flow (Scheduler DAG)

## Daily Flow

1. `00_ingest_market_and_account`
- pull prices, portfolio state, broker account status

2. `01_mark_sleeve_nav`
- mark sleeve positions and refresh sleeve equity/cash snapshots

3. `02_run_signals_all_strategies`
- run incumbent and challenger strategies (and parameter variants)

4. `03_score_incumbent_vs_challengers`
- compute score components over configured window

5. `04_rotation_decision`
- apply gates, cooldowns, and produce assignment changes

6. `05_build_position_targets_by_sleeve`
- convert selected strategy intents into target positions

7. `06_pretrade_risk_gate`
- enforce sleeve and portfolio risk checks

8. `07_submit_ibkr_orders`
- submit orders to IBKR paper account

9. `08_reconcile_fills_update_ledgers`
- ingest executions and update sleeve orders, fills, positions, ledgers

10. `09_postclose_metrics_and_attribution`
- compute daily performance/risk/attribution metrics

11. `10_emit_report_and_alerts`
- publish daily operator report and anomaly alerts

## Weekly Flow

1. `W1_strategy_parameter_leaderboard`
2. `W2_promotion_retirement_review`
3. `W3_allocation_reweight_review`

## Monthly Flow

1. `M1_risk_budget_rebaseline`
2. `M2_parameter_range_governance_update`
3. `M3_long_horizon_performance_audit`

## Risk and Safety Controls

Must-have controls:

- max gross/net exposure
- max sleeve position size
- max symbol/sector concentration
- daily account loss stop
- kill switch for data staleness, reconciliation mismatch, or API anomalies
- order rejection handling and retry policy
- strict audit logging for all rotation and risk decisions

## Continuous Improvement Loop

Daily:

- attribution and execution quality review
- detect slippage, fee drag, and constraint-induced performance decay

Weekly:

- compare incumbents vs challengers by market regime
- investigate degraded sleeves and drifted parameters

Monthly:

- retire weak variants
- promote resilient challengers
- update risk budgets and parameter bands

## Acceptance Criteria

System is considered successful when:

1. Daily IBKR paper workflow runs end-to-end without manual intervention for defined burn-in period.
2. Sleeve accounting reconciles with broker account state within defined tolerances.
3. Rotation events are explainable, threshold-based, and fully logged.
4. Risk controls prevent breaches and trigger deterministic safeguards.
5. Performance reports support strategy promotion/retirement decisions.
6. Config versions enable reproducible decisions and post-hoc audits.
